# 3D 팀 스페이스 - 2 디자인 검토 기록

작성일: 2026-11-02

## 목적과 판단 범위

팀의 연결 상태를 빠르게 파악하고, 팀원과 에이전트의 소유 관계를 이해하며, 필요한 에이전트의 정보를 살펴보는 화면이다. 새 디자인의 목표는 3D 조형물을 대시보드에 추가하는 데서 벗어나 이 관계 자체를 공간으로 표현하는 것이다. 최종 시각 방향은 Apple·Samsung·Google의 현대적 인터페이스 원칙을 참고한 간결함, 명확함, 정돈된 여백과 읽기 쉬운 정보 위계다.

‘AI Slop’은 표준화된 품질 점수나 제작 방식을 판별하는 검사가 아니다. 특정 색, 글꼴, 카드가 등장했다는 이유만으로 디자인의 출처나 품질을 단정할 수 없다. 아래 진단은 기존 화면과 이 서비스의 목적에 대한 설계 판단이다. 패턴을 없애는 알고리즘만으로 인간적인 느낌이나 독창성을 보장할 수 없으며, 실제 화면과 사용 동선을 보면서 수정해야 한다.

## 조사에서 얻은 기준

### 1. 금지 목록만으로는 고유한 디자인이 생기지 않는다

Paul Bakaus는 모델의 반복 습관이 시대에 따라 바뀌며, 보라색 그라데이션의 대안으로 유행한 베이지 배경과 이탤릭 세리프도 새로운 기본값이 될 수 있다고 설명한다. 특정 스타일을 다른 스타일로 치환하는 것보다 화면의 목적에 맞는 결정을 유지하는 것이 중요하다. 이번 수정은 베이지·세리프를 새 유행처럼 가져오는 방식으로 진행하지 않는다.

출처: [Paul Bakaus — Impeccable by Design](https://www.paulbakaus.com/impeccable-by-design/)

### 2. 반복되는 구성과 과잉 포장이 함께 문제를 만든다

Impeccable의 사례집은 동일한 히어로·지표·기능 격자, 중첩 카드, 장식용 아이콘 타일, 네온 효과, 불필요한 설명의 반복 등을 검토 대상으로 삼는다. 원문도 개별 검출 항목을 맥락에 따라 판단해야 한다고 설명한다. 기존 페이지에서는 이 패턴들이 동시에 나타나 팀 도구보다 범용 SaaS 소개 화면처럼 보였다.

출처: [Impeccable — Slop catalog](https://impeccable.style/slop/)

### 3. 정보는 조작하기 전에 이해할 수 있어야 한다

Bret Victor의 정보 소프트웨어 관점에서는 사용자가 계속 조작하게 만들기보다 맥락에 맞는 시각적 정보를 먼저 제공하는 것이 중요하다. 이 화면에서는 팀원 이름, 소유 에이전트, 온라인·오프라인 상태가 기본 공간에서 보여야 한다. 세부 설명을 읽기 위한 선택은 유지하되, 전체 현황까지 여러 번 눌러야 알 수 있게 만들지 않는다.

출처: [Bret Victor — Magic Ink](https://worrydream.com/MagicInk/)

### 4. 공간은 기억과 관계를 돕는 표현 수단이다

Kinopio 제작자는 정보를 직접 배치하고 연결하는 과정과 공간 기억의 관계를 설명한다. 또한 툴바와 획일적인 표현이 많아지는 문제를 지적한다. 이번 적용에서는 팀원별 위치와 인덱스를 일관되게 유지하고, 필터가 바뀌어도 위치를 임의로 재배열하지 않는 쪽을 선택했다. 이는 Kinopio를 시각적으로 복제하는 것이 아니라 해당 원리를 DevLink의 데이터에 적용한 판단이다.

출처: [Kinopio — About and design approach](https://kinopio.club/help/about/)

### 5. 개체와 관계가 인터페이스의 구조를 정해야 한다

Are.na는 콘텐츠를 수집하고 배치하며 연결하는 행위를 제품의 핵심으로 설명한다. 여기서 가져온 기준은 범용적인 네트워크 장식을 만드는 대신 실제 개체의 관계를 형태로 드러내는 것이다. DevLink의 현재 데이터가 제공하는 관계는 팀·팀원·소유 에이전트다. 따라서 공간의 모듈과 묶음도 이 관계를 기준으로 만든다.

출처: [Are.na — About](https://www.are.na/about)

### 6. 전체 파악과 상세 탐색을 분리하되 맥락은 유지한다

Shneiderman의 원 논문은 전체 개요, 확대·필터, 요청 시 상세 정보라는 흐름을 제시하며 이를 출발점이라고 표현한다. 3D 공간에서는 가림과 방향 감각도 고려해야 한다고 설명한다. 따라서 팀 전체를 볼 수 있는 시점과 이름표를 유지하고, 선택 상세 정보는 필요한 순간에 노출한다. 그래픽 위치를 모르는 사용자에게는 이름 기반 검색과 명단도 제공한다.

출처: [Ben Shneiderman — The Eyes Have It, University of Maryland 원문 PDF](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf)

### 7. 부가 기능을 숨기는 것과 주요 기능을 숨기는 것은 다르다

NN/g는 자주 필요한 기능은 기본 화면에 두고 덜 필요한 기능을 요청 시 공개하되, 이동 방법과 이름이 명확해야 한다고 설명한다. 이 화면에서는 팀 선택·연결 상태·팀원 선택을 기본으로 남긴다. 에이전트의 긴 설명·닉네임·참여일은 선택 상세로, 이름·프로젝트 검색과 전체 명단은 명확한 버튼으로 여는 탐색 영역으로 옮긴다.

출처: [Jakob Nielsen — Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)

### 8. 공간 UI에도 키보드와 포커스의 대안이 필요하다

tldraw의 공식 문서는 캔버스 포커스와 일반 페이지 입력을 구분하고, 집중 모드에서 주변 UI를 최소화하는 방법을 설명한다. W3C의 키보드 접근성 해설은 포인터 동작에 대응하는 키보드 방법을 제공하도록 안내한다. DevLink에서는 에이전트 선택을 이름표·명단의 실제 버튼으로도 제공하고, 검색 입력 중에는 공간 단축키가 입력을 가로채지 않도록 해야 한다. 명단이 있다는 사실만으로 전체 접근성 준수를 주장하지는 않는다.

출처: [tldraw — Focus](https://tldraw.dev/sdk-features/focus), [tldraw — Instance state](https://tldraw.dev/sdk-features/instance-state), [W3C — Understanding Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)

### 9. 현대적 미니멀 UI는 콘텐츠와 조작의 구분에서 시작한다

Apple의 WWDC25 설명은 콘텐츠를 넓게 보여주는 영역과 그 위의 탐색·조작 레이어를 구분하고, 배경이 달라져도 조작 요소의 식별성과 가독성을 유지하는 데 초점을 둔다. 이 화면에서는 3D 관계도를 콘텐츠로, 팀 선택·필터·시점 조작을 별도의 UI로 구분하는 원칙을 참고한다. 모든 카드에 유리·굴절·블러를 복제하라는 의미로 적용하지 않는다.

출처: [Apple — Meet Liquid Glass, WWDC25](https://developer.apple.com/videos/play/wwdc2025/219/)

Samsung의 One UI 기본 원칙은 현재 작업에 집중하도록 돕는 단순한 설계, 자연스러운 조작, 편안한 가독성, 화면 크기에 맞는 배치를 강조한다. One UI 7 소개도 일관되고 간결한 구성으로 정보의 위계를 분명히 하는 방향을 설명한다. 따라서 이 페이지에서는 어두운 네온, 복잡한 모형의 세부 묘사, 작은 장식 글자보다 글자 크기·간격·표면 구분을 먼저 다듬는다. 모바일에서는 같은 정보를 유지하면서 조작 위치와 상세 표시 방식을 조정한다.

출처: [Samsung Developer — One UI Overview](https://developer.samsung.com/one-ui/index.html), [Samsung Design — One UI 7](https://design.samsung.com/global/contents/one-ui-7/)

Google Material 3는 표현적인 모션과 기능 중심의 표준 모션을 구분하며, 실용적 제품에는 바운스가 적은 표준 모션을 안내한다. DevLink에서는 반복 부유·회전·통통 튀는 움직임보다 선택 반응, 시점 변경, 정보 시트 열림처럼 조작 결과를 설명하는 짧고 절제된 전환을 사용한다. 이는 Material의 시각적 테마를 그대로 적용하거나 특정 모션 구현을 채택했다는 뜻은 아니다.

출처: [Google — Material 3 Motion](https://m3.material.io/styles/motion/overview/how-it-works)

## 기존 화면 진단과 변경 방향

| 기존 화면에서의 진단 | 변경 방향 | 기대하는 사용상 효과 |
| --- | --- | --- |
| 큰 홍보성 제목과 영어 머리말이 작업보다 먼저 보임 | 실제 팀 이름과 기능 이름을 중심으로 간결하게 표시 | 현재 살펴보는 팀을 바로 인지 |
| 지표 카드 띠가 화면 상단을 크게 차지함 | 팀원·에이전트·연결 상태를 작은 인라인 정보로 통합 | 공간에 화면을 배분하면서 기본 현황 유지 |
| 3D가 둥근 카드 안의 콘텐츠처럼 취급됨 | 전체 페이지의 주요 작업면을 공간으로 사용 | 3D를 탐색의 중심으로 전환 |
| 상시 우측 패널이 평범한 대시보드 구도를 만듦 | 선택했을 때만 단일 상세 시트를 표시 | 전체 구조를 먼저 보고 필요한 정보에 집중 |
| 이름·프로젝트 목록과 3D 이름표가 계속 중복됨 | 명단·검색은 열고 닫는 탐색 영역으로 제공 | 동일 정보가 경쟁하는 현상 완화 |
| 추상적인 중앙 허브와 방사형 선이 실제 데이터에 없는 중심성을 만듦 | 중앙 토러스·허브를 없애고 팀원별 모듈로 구성 | 존재하는 소유 관계를 직접 표현 |
| 귀여운 로봇과 별도 로봇 초상화가 의미 없이 반복됨 | 도구별로 구분되는 얇고 간결한 에이전트 타일을 선택 대상으로 사용 | 도구의 차이를 식별하면서 부가적인 캐릭터 해석 제거 |
| 네온·블룸·그라데이션이 여러 표면에서 주목을 요구함 | 밝은 중립 작업면과 흰색·실버·그래파이트 표면, 제한된 상태·선택 색 | 상태와 선택을 구분하기 쉬운 시각적 위계 |
| 카드·테두리·둥근 모서리·그림자가 여러 겹 겹침 | 평평한 명단과 필요한 단일 정보 표면으로 정리 | 정보보다 포장이 두꺼워지는 문제 완화 |
| 기능적 이유가 약한 영문 소제목과 작은 장식 라벨이 많음 | 읽기 쉬운 기존 한글 산세리프와 기능적 인덱스로 정리 | 새 서체 유행에 기대지 않고 내용의 위계 확보 |
| 모든 에이전트를 애니메이션과 장식으로 동등하게 강조함 | 선택·상태·사용자 조작에 반응하는 제한된 움직임 적용 | 비교와 탐색 중 시선 분산 감소 |
| 3D 조작만으로 정보를 찾아야 할 가능성이 있음 | 버튼 이름표, 팀원 명단, 검색, 시점 복귀, 축소 모션과 대체 화면 유지 | 다양한 입력 방식으로 같은 정보에 접근 |

## 선택한 구조

- 전체 페이지를 팀 연결 공간으로 구성한다. 차별점은 장르적 장식이 아니라 소유 관계를 직접 탐색하는 공간 구조에서 만든다.
- 왼쪽에는 상자를 두르지 않은 간결한 팀원 명단을 둔다. 각 팀원의 인덱스는 공간의 묶음과 대응한다.
- 공간의 에이전트는 흰색·실버·그래파이트의 얇고 단순한 둥근 타일로 표현하며, 사용 도구별 차이를 구분한다. 팀원별 안정적인 배치와 읽기 쉬운 이름표가 소유 관계를 나타낸다.
- 복고풍 PC, 로봇, 네온, 물리적 명판·나사 같은 소품은 표현 수단으로 사용하지 않는다. 추상적인 중심 허브와 장식용 네트워크도 두지 않는다.
- 선택 전에는 팀의 구조와 상태가 우선이다. 선택 후에만 도구·프로젝트·설명·소유 팀원을 담는 한 장의 상세 시트가 나타난다.
- 검색과 전체 에이전트 명단은 명확한 이름의 버튼으로 여는 탐색 영역에 둔다.
- 기본 작업면 `#f5f5f7`, 본문 `#1d1d1f`, 주요 선택·조작 강조 `#0066cc`를 기준으로 구성한다. 색상은 상태와 선택을 구분할 때 우선 사용한다. 베이지 배경·세리프 제목을 새로운 고급스러움의 공식으로 도입하지 않는다.
- 시각적 우선순위는 명확한 정보 위계, 읽기 쉬운 크기와 대비, 충분한 여백, 콘텐츠와 조작의 분리다. Apple·Samsung·Google의 개별 장식을 섞어 복제하는 대신 공통된 사용성 원칙을 이 제품에 맞게 적용한다.
- 움직임은 사용자 조작과 정보 전환을 설명하는 범위로 제한한다. 화면 크기에 맞는 배치, 키보드 입력과 축소 모션 설정도 함께 고려한다.
- 팀원 수, 에이전트 수, 온라인 상태, 프로젝트 수는 기존 샘플 데이터로 계산한다. 작업량·트래픽·최근 활동·실시간 동기화처럼 제공되지 않는 데이터를 만들지 않는다.

## 확인할 사용 흐름

1. 첫 화면에서 팀 이름, 팀원 구분, 온라인·오프라인 상태를 파악할 수 있는가.
2. 팀원 선택 시 해당 소유 에이전트가 분명해지고 다른 위치의 맥락이 유지되는가.
3. 에이전트 선택, 상세 정보 닫기, 전체 시점 복귀가 예측 가능한가.
4. 명단과 검색으로도 3D 개체를 선택할 수 있는가.
